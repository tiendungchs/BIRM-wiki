# G107 — The exchange rate between computation and accuracy is a hand-set constant in every architecture that varies its own compute

**Status:** `OPEN`  
**Kind:** `part`  
**Level:** `L3`  
**Registry:** [[wiki/architectural-gaps.md]]  
**Closes when:** An architecture sets its own price on computation from a quantity it measures or computes at run time, and its per-input compute tracks task difficulty across at least an order of magnitude without a per-task sweep of that price.

## Why it blocks the target

Every mechanism in the wiki that spends a variable amount of computation per input needs to know what a step of thinking is worth relative to a point of accuracy, and none of them can find out. Adaptive computation time makes the budget differentiable and then hands the trade-off to a scalar `τ` that its own author reports the network is "quite sensitive" to, requiring a 20-seed logarithmic grid per task ([[wiki/concepts/adaptive-computation-time.md]]). The sampling-based half of the literature has the same hole under a different name — [[wiki/concepts/external-verification.md]] names adaptive allocation as its open control problem and no source supplies a policy — and the biological stopping rules push the constant one level down rather than removing it, since a decision threshold fixes the error rate and nothing sets the error rate ([[wiki/concepts/evidence-accumulation.md]]). A reasoning system that cannot price its own deliberation cannot be deployed on a task distribution of mixed difficulty, which is every interesting one.

## Best current answer

None that removes the constant. The one substitution attempted since makes the point: [[wiki/entities/universal-transformer.md]] drops the ponder penalty `τ` entirely and stops on a hand-set **threshold** plus a step cap, with no sweep and no sensitivity analysis reported — the price changed form and stayed external. What it does add is the first evidence for the row's *second* clause independently of its first: per-position compute tracks a counted ground-truth quantity (mean ponder 2.3/3.1/3.8 steps for bAbI questions requiring 1/2/3 supporting facts) without the price being learned, so difficulty-tracking and price-setting are separable and only the latter is still open. Against that, the same source's depth-matched controls raise the possibility that the gain is regularisation rather than allocation ([[wiki/empirical-tensions.md]] T321), which would make the tracking evidence weaker than it looks.

Three partial routes: `τ` is at least *interpretable* (a cost per state transition), so it could in principle be set from a real budget if computation and error were commensurable — the source's own suggestion, and it requires an external price rather than an internal one. Higher `τ` was found to improve sample efficiency on addition, so the constant is not purely a cost knob and a naive "set it as low as affordable" is wrong. And the one-sided-penalty result for the accumulator gain `g*` ([[wiki/concepts/evidence-accumulation.md]]) shows what the target property looks like: a parameter that only needs saturating, not estimating. No compute-price parameter in the wiki has been shown to be one-sided. **The same constant on the width axis, in an architecture that already computes the test it would need to drop it** (Goyal et al. 2019, [[wiki/entities/rims.md]]): `k_A` of `k_T` recurrent modules update per step, with a stated trade-off in both directions — too few active modules hurts optimisation, too many attenuates the out-of-distribution gain — and the authors name "dynamic ways of controlling how many RIMs to activate" as future work. The unexploited part is that the selection already runs a **per-module threshold test**: each module attends over the input with a null row appended and is ranked by how little mass it puts on that null row. Activating every module that beats its *own* null row, instead of taking a fixed-size top-`k_A` over the ranking, would make the active-set size an input-dependent quantity computed at run time with **no price scalar at all** — this row's `Closes when` on the width axis, one line of code away, and unrun.

## Status

`OPEN` — the parameter is acknowledged as a weakness by the source that introduced it and has not been removed by anything since in the wiki. Note that it is *not* the same row as `G24`: a planning horizon asks how far ahead to look in a modelled world, this asks what a unit of thinking costs, and an architecture could answer either without answering the other
